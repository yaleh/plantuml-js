## Proposal

纯 TS PlantUML class 图渲染库 `@yalehwang/plantuml-js` 的 M1 里程碑：从一个空仓起步，搭好 npm 包脚手架，交付 `render("@startuml\nclass A\n@enduml")` 产出正确 SVG 的最小纵向切片。四层架构（API → Parser → Model IR → LayoutEngine → SVG Renderer）在本阶段全部打通，但每一层只覆盖最小子集：parser 识别 `@startuml`/`@enduml` 与 `class`/`interface`/`enum`/`abstract class` 单行声明；IR 承载 entities/relations/packages；LayoutEngine 做成可插拔纯函数接口，默认 elkjs 实现（单实体也走真实 elkjs 布局）；SVG 发射器画出类框与文本。成员、关系、泛型、package 分组、正交边路由、文本度量留到 M2。

## AC

- [x] `npm test`（vitest）通过，`npm run typecheck` 通过
- [x] `render("@startuml\nclass A\n@enduml")` 返回对象含 `svg` 字符串：以 `<svg` 开头、包含代表 class A 的类框与文本 "A"；`diagramType === "class"`
- [x] parser 识别 `@startuml`/`@enduml` 与 `class`/`interface`/`enum`/`abstract class` 单行声明，产出 entities 条目且类型与名字正确
- [x] `LayoutEngine` 是纯函数接口 `layout(model) => LayoutResult`；默认 elkjs 引擎对单实体产出非零 width/height 与坐标
- [x] 输出确定性：同一 puml 输入连续渲染两次，svg 字节一致
- [x] SVG 是合法 XML（能被解析器接受；类名/文本中的 `<`、`&` 被正确转义）

## DoD

不是"能 import、能在 console 打点东西"就算完成。`render()` 端到端把一段 puml 变成能被解析、包含真实类框与文本的 SVG，且被 vitest 断言覆盖；LayoutEngine 接口真正可替换（注入一个 stub 引擎后布局结果随之改变，证明不是写死的绘制路径）。npm 包元数据（name `@yalehwang/plantuml-js`、MIT、type:module、main/exports）就位，`npm test` 与 `npm run typecheck` 均绿。
